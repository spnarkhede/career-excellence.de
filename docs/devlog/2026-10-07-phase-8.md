# 2026-10-07 — Phase 8 — v0.9.0

## What changed

Rewrote `resetPassword`'s token consumption to the same atomic-`updateMany`
pattern already used for OTP (BUG-009) and refresh-token rotation — the
Phase 4 implementation consumed a token via a separate read-then-`update`,
letting two concurrent submissions of the same token both succeed (BUG-012).
Added structured error codes (`RESET_TOKEN_INVALID`/`USED`/`EXPIRED`) and a
failure `auth_event` for each, previously recorded only on success. Added a
confirmation email on every successful reset.

Added a per-email resend cooldown and previous-token invalidation to
`requestPasswordReset`, matching the OTP/magic-link resend pattern, and
narrowed (though didn't fully close — see FINDINGS.md) the timing gap
between known and unknown emails. Added `@Throttle` to
`POST /auth/password-reset/confirm`, which had no rate limiting at all
(BUG-013) — every sibling verify/confirm endpoint already had one.

Wired both the reset-request email and the new password-changed confirmation
email through apps/worker's existing BullMQ email queue, via a new
`apps/api/src/common/email-queue.ts` producer — previously every email in the
codebase, including these, sent synchronously in-request despite the queue
already existing and running in apps/worker. The producer creates its Redis
connection lazily (on first use, not at module import) specifically because
every existing test file transitively imports it via `auth.service.ts`, and
an eager connection would have attempted to reach Redis in every one of them.

Rewrote the reset-password page to match the verify-email/magic-link
pattern: the token is stripped from the address bar after being read,
`referrer: no-referrer` is set, and three distinct token-failure states
(expired/used/invalid) each render with a "Request a new link" affordance
instead of one generic error message. Redirect-on-success now goes through
the shared `isAllowedRedirect`/`next`-param helper instead of a hardcoded
`/login` path.

## Why

A password-reset token is a bearer credential with the same single-use
requirement as an OTP code, so the same "exactly one succeeds under
concurrency" guarantee has to hold — and didn't, until this phase's own test
requirement ("two simultaneous submits with one token, exactly one succeeds")
caught it. Queueing the reset/confirmation emails and rate-limiting the
confirm endpoint are both explicit task requirements this phase's spec
called out by name, closing gaps that had sat unaddressed since the Phase 4
implementation first shipped them.

## Open issues

- Same database limitation as every prior phase, plus no browser testing of
  the rewritten reset-password page's token-failure states.
- Timing-safety tradeoff flagged, not resolved: `requestPasswordReset`'s
  enumeration protection narrows but doesn't fully close a timing
  side-channel — see FINDINGS.md for why (no single dominant slow operation
  to equalize against, unlike `login()`'s dummy-hash approach) and what
  closing it fully would require.
- Queue adoption is scoped to this phase's two email sends only; every other
  email type in the codebase still sends synchronously, unchanged — a
  deliberate scoping decision, not an oversight.
- Carried forward: the remaining open architecture questions from Phase 1,
  and D6 (TOTP MFA, still unresolved/unimplemented).
