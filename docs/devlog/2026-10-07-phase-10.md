# 2026-10-07 — Phase 10 — v0.11.0

## What changed

Implemented role-based access control enforcement, route guards, and safe
routing/redirect logic across apps/api, apps/web, and apps/admin.

On the API: a declarative `@RequirePermission`/`PermissionsGuard` pair for
NestJS controllers (applied to `ProfileController`), loading roles and
permissions from the server-resolved principal (a database join via the
pre-existing `PrincipalService`) — never from anything client-supplied.
Converted `revokeSession`/`unlinkAccount` from a silent no-op into an
explicit 404 when the target resource doesn't exist or belongs to a
different user — the same 404 either way, since a 403 would leak that the
resource exists at all for someone else.

On apps/web and apps/admin: `requireUser()`/`requirePermission()` server
component helpers that re-fetch the principal fresh on every page load and
delegate the "where do I redirect?" decision to one new, pure,
exhaustively-tested function, `resolveAuthRedirect()` (in `@saas/security`),
rather than two independently-written page implementations hoped to stay in
sync. A new `isSafeRelativePath()`/`safeReturnTo()` pair closes the open-
redirect class of bug: decode exactly once, reject backslashes, control
characters, `//`, absolute schemes, and anything outside an optional
allowlist, falling back to `/dashboard`. apps/admin gained middleware for
the first time (it had none before this phase) plus a `/forbidden` page for
apps/web.

Added a static-analysis route-matrix test (`scripts/route-matrix.ts`/
`route-matrix.spec.ts`, 84 assertions) as the practical proxy for "a route
matrix generated from the codebase... unclassified new routes fail the
test" — there's no live database or running server in this environment for
a real 4-persona HTTP crawl, so this discovers every controller handler and
page via regex and cross-checks it against a hand-maintained manifest; a
new, unclassified route or a drifted guard both fail. Manually verified
this actually catches a regression (not just discovers routes) by
temporarily removing a guard and confirming the suite failed, then
reverting.

Added `apps/api/test/phase10-forged-headers.spec.ts`, the task's explicit
test 5: constructs forged `x-middleware-subrequest`/`x-user-id`/
`x-user-role`/`x-principal` headers and an unsigned `alg:none` JWT-shaped
cookie, confirms `SessionGuard` rejects all of them regardless, since it
only ever reads the actual session cookie.

Found and fixed two real bugs. **BUG-015**: `ForbiddenError` is a plain
`Error`, not a Nest `HttpException`, so it fell through
`AllExceptionsFilter`'s generic branch and returned HTTP 500 instead of 403
for every permission-denied case — this phase's new `PermissionsGuard`
pattern was expected to make this common going forward, so it was fixed
before it spread further. **BUG-016**: `apps/web`'s middleware hardcoded
the unprefixed session cookie name, but Phase 7's `__Host-` cookie-
prefixing means the real cookie name in any production-shaped deployment is
`__Host-app_session` — this middleware would never have detected a
signed-in user in production, locking out every user. Also caught and fixed
a redirect-loop bug in `resolveAuthRedirect`'s own first draft (an
authenticated visit to `/login?next=/login` bounced back to `/login`)
before it was ever used in a real page — caught by the function's own
exhaustive test suite.

## Why

Framework middleware has had real bypass bugs (CVE-2025-29927, a forged
`x-middleware-subrequest` header in Next.js) — the task's "guards in
layers" principle treats middleware as an outer, UX-only layer and requires
every API handler, page, and admin route to independently re-verify
server-side. The object-level 404-vs-403 convention and the safe-redirect/
no-loop invariant are the same class of security property every prior
phase's checklist has centered on: closing a specific, well-understood
class of bypass or leak, each independently testable.

## Open issues

- No live browser in this session: back/forward-button behavior after
  logout (the task's explicit test 4), refresh behavior on a protected
  page, and the full deep-link-survives-login round trip were never
  exercised — no apps/web/apps/admin test runner exists in this monorepo
  at all to even attempt an automated version.
- No dynamic (`[id]`-style) route with its own object-level ownership
  check exists yet beyond `revokeSession`/`unlinkAccount` — checklist item
  6 ("Dynamic routes") is N/A rather than tested; a future phase
  introducing one should re-visit this.
- No server actions exist anywhere in this codebase (verified during
  research) — the route-matrix test's own doc comment flags this so a
  future server action is caught as "unclassified" the moment one appears.
- Duplicated `requireUser()`/`requirePermission()` logic between apps/web
  and apps/admin, deliberately not extracted into a shared package this
  phase (out of scope — "do only the work in this phase").
- `settings.manage` permission remains unused (carried forward from
  Phase 3's seed data) — worth a human decision on removing it or building
  a feature that uses it.
