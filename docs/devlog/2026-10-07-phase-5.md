# 2026-10-07 — Phase 5 — v0.6.0

## What changed

Rewrote `AuthService.login`: an unknown email is now compared against a fixed-cost
dummy hash (computed once at startup) instead of short-circuiting, so response
timing no longer reveals account existence; every account-status check
(disabled/deleted/locked/pending_verification) moved to run only after the password
is confirmed correct; account lockout now grows (doubling, capped at 24h) instead of
a single fixed window; a successful login now discards whatever session the
caller's existing cookie pointed at (session fixation prevention).

Replaced `@nestjs/throttler`'s in-process-memory storage with a Redis-backed
implementation, applied globally — the previous default violated this phase's
explicit "never process memory" requirement for every throttled route, not only
login. Changed `ZodValidationPipe` to return 422 (not 400) with per-field messages,
and taught the global exception filter to map Prisma connection failures to 503 with
a safe message and to set `Retry-After` when appropriate.

On the client: added request timeout and offline detection to `@saas/api-client`,
added a double-submit guard and an already-authenticated redirect to the login page
(both re-deriving state from the server, never assuming), and hardened the
dashboard so any `/auth/me` failure other than "not authenticated" shows a visible
retry state instead of a blank page or crash.

Writing this phase's own tests surfaced a second real bug (BUG-008, alongside
Phase 4's BUG-007): `locked`/`disabled`/`deleted` status was also being checked
before the password, the same enumeration pattern the phase's own spec names
explicitly ("Account states, checked only after the password matches").

## Why

This phase's explicit goal is a login endpoint that leaks nothing about account
existence or state to an unauthenticated caller, rate-limits meaningfully across
multiple API instances (not just one process's memory), and degrades gracefully
under network/server failure on the client. Each of these is independently testable
and independently a real security property — writing the test for "account states
checked only after the password matches" is literally what surfaced BUG-008, the
same way Phase 4's test for "unverified login" surfaced BUG-007.

## Open issues

- Same database limitation as Phases 3/4, plus a new one: this phase's checklist
  includes several items (double-click guard, multi-tab, offline mode in a real
  browser, slow-network throttling) that genuinely need browser automation, which
  wasn't run this session either. See `docs/auth/PROGRESS.md` for the itemized
  breakdown of what's "Confirmed working" (the handful that needed neither a
  database nor a browser) versus "Requires manual verification."
- `RedisThrottlerStorage` fails closed on a Redis outage — every throttled route
  starts rejecting rather than silently allowing unlimited requests. Correct per the
  "never process memory" requirement, but worth flagging for production-readiness
  planning (a Redis outage becomes a login-availability incident).
- No external OAuth/auth-provider SDK is wired yet, so checklist item 16
  ("Auth-provider error") has nothing to test against.
