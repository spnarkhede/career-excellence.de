# 2026-10-07 — Phase 6 — v0.7.0

## What changed

Rewrote `AuthService.requestOtp`/`verifyOtp`: the 6-digit code's consumption step is
now a single atomic `updateMany` guarded by `usedAt: null` (instead of a separate
`findFirst` then `update`), resend invalidates any previous unused code before
issuing a new one, a 30-second per-destination cooldown governs resends, and a
successful verification discards whatever session the caller's existing cookie
pointed at (the same session-fixation prevention added to `login()` in Phase 5).

Added `requestMagicLink`/`verifyMagicLink`, implementing the 32-byte-token half of
this phase's task list alongside OTP. This pragmatically resolves open question D4
("Email OTP, magic link, or both?") by implementing both rather than waiting on a
human pick — the Phase 6 task list itself specified both mechanisms (task 1 offers
"6+ digit code... or a 32 byte magic link token"; task 6 is entirely about magic
links). Magic link reuses the same atomic-consume and cooldown/invalidate-on-resend
pattern as OTP, without an attempt counter (token entropy makes guessing infeasible).

On the client: added a magic-link confirm page (Confirm button + POST, mirroring
Phase 4's verify-email page, so a link scanner's GET request can't consume the
token) and an OTP request/verify page (single input, `autocomplete="one-time-code"`,
numeric input mode, native paste support, a 30-second resend countdown, distinct
error states).

Writing this phase's own concurrency test surfaced a real bug (BUG-009): the
pre-existing `verifyOtp` could let two concurrent correct submissions of the same
code both succeed, each issuing its own session — exactly the race this phase's
"concurrent use of one code, exactly one succeeds" test requirement exists to catch.

## Why

A one-time code or magic-link token is only as strong as its single-use guarantee;
Phase 6's explicit task list and test list both center on that guarantee (atomic
consume, attempt limits, resend invalidation, enumeration safety) because an OTP
mechanism that can be reused, brute-forced, or distinguished from "unknown
destination" defeats the point of having one. Implementing both OTP and magic link
rather than blocking on D4 keeps the workstream moving without overriding the
human's eventual choice — `one_time_tokens.purpose` already separates the two
cleanly, so either can be disabled later with no schema change.
