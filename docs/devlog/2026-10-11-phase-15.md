# 2026-10-11 — Phase 15 — v0.16.0

## What changed

Built the SEO and sharing surface for launch: unique, correctly-sized meta
titles/descriptions and canonical URLs on every public and auth-flow page,
a 1200x630 social preview image, a full favicon/icon/manifest set (none
of it existed before this phase), a sitemap limited to genuine public
pages, and `noindex` on every auth/account/dashboard page.

- **Meta titles/descriptions/canonical**: added
  `apps/web/src/lib/seo.ts`'s `buildPageMetadata()`, called from all 14
  public and auth-flow pages. It builds a complete, self-contained
  `Metadata` object per page (title, description, canonical, OpenGraph,
  Twitter) rather than relying on Next's parent/child metadata merge —
  which REPLACES, not deep-merges, a nested object like `openGraph` the
  moment a child page sets any field on it, a documented Next.js gotcha
  that would otherwise have silently dropped inherited OG fields on every
  page that set its own title. Every title lands in 50-60 characters and
  every description in 120-160 characters, measured against a live
  server (not estimated) — see the exact per-page counts in
  `docs/auth/COMPONENTS.md`.
- **Client-only auth pages couldn't carry metadata**: `login`, `signup`,
  and `forgot-password` were each a single `"use client"` file, and a
  client component cannot export `metadata` at all. Split each into a
  thin server `page.tsx` (metadata only) + `*-client.tsx` (the unchanged
  interactive form), the exact pattern already used by
  verify-email/magic-link/reset-password/otp.
- **Social preview image**: `apps/web/src/app/opengraph-image.tsx`, a
  1200x630 `next/og` `ImageResponse` placed at the app root so Next's
  file-convention metadata resolution applies it to every page that
  doesn't define its own — zero binary image authoring, zero new
  dependency (next/og ships with Next.js).
- **Favicon/icon/manifest** — fully greenfield, no `public/` directory or
  any icon file existed in either app before this phase:
  `favicon.ico` (a real, hand-built 16x16 32bpp ICO, written byte-for-byte
  via a one-off Node script since no image library is installed and
  Next's dynamic-icon convention can't produce that literal filename/
  format), `icon.svg` (hand-written vector), `apple-icon.tsx` (180x180,
  `next/og`), and `manifest.ts` (192/512 icons via two plain custom route
  handlers + `theme_color`).
- **Sitemap/robots/noindex**: rewrote `sitemap.ts` from a stale,
  incomplete hand list down to exactly the 4 genuine marketing pages
  (`/`, `/contact`, `/privacy`, `/terms`) — deliberately NOT derived from
  `scripts/route-matrix.ts`'s `discoverPages()`, since that script
  answers "does this page require authentication," not "does this belong
  in a sitemap" (every auth-flow page is unauthenticated-reachable but
  still doesn't belong in search results). Added `robots: {index:false,
follow:false}` to all 10 auth-flow pages plus one shared
  `apps/web/src/app/dashboard/layout.tsx` covering all 3 dashboard
  routes from a single file — the same pattern `apps/admin`'s root layout
  already used app-wide. Added `apps/admin/src/app/robots.ts` (disallow
  `/` entirely) as pure defense-in-depth on top of that pre-existing
  layout-level noindex.

## Why

The task list draws a hard line between what's advisory (robots.txt) and
what's enforced (meta tags, server-side auth checks) — "robots.txt is not
a security control; protection stays on the server" is stated explicitly.
Every choice above follows that: `robots.ts`'s own comment and
`dashboard/layout.tsx`'s both say so directly, and the real exclusion
mechanism for every auth-flow/dashboard page is its own `noindex` meta
tag, not the robots.txt disallow list (which only covers `/dashboard`
advisorially). Likewise, the sitemap is hand-maintained rather than
auto-derived, because the two "public" classifications (authorization vs.
search-worthiness) are genuinely different questions, and conflating them
would have put every login/OTP/password-reset page into search results.

## Bug found and fixed before committing

**BUG-027** (see `docs/auth/FINDINGS.md`): `metadata.themeColor`,
written in the root layout's first draft, is silently ignored by Next 15
— the field was removed from the `Metadata` type in Next 14+ and moved to
a separate `viewport` export. No build or type error flags this mistake;
it was caught by checking the installed Next version against the API
actually used, then confirmed fixed by inspecting the live-rendered
`<head>` for the resulting `<meta name="theme-color">` tag.
