# 2026-10-07 — Phase 12 — v0.13.0

## What changed

Built the full error-handling catalog and closed real gaps in it.

Added `docs/auth/ERRORS.md` — the response shape, the single mapping
layer (`AllExceptionsFilter`) from provider/database/throttler exceptions
to catalog codes, recovery paths, logging/scrubbing, and metrics/alerts —
and its machine-checkable counterpart, `apps/api/src/common/error-catalog.ts`
(`AUTH_ERROR_CATALOG`), so a test can assert real thrown exceptions match
the documented status/message rather than relying on a human cross-read.

Added `recordAuthMetric()` (`packages/observability/src/metrics.ts`) —
structured log-based metric events (`login_failure`, `login_success`,
`rate_limited`, `refresh_reuse_detected`, `auth_5xx`, `email_send_failed`),
wired at six real call sites in `auth.service.ts` and
`all-exceptions.filter.ts`. No managed metrics backend exists in this
codebase, so this is the plumbing a future Prometheus/Datadog integration
would key off of, not the integration itself — documented honestly as
**Requires configuration** for the alerting layer.

Fixed BUG-025: six auth exceptions (ten throw sites — wrong login
password, refresh-token reuse/expiry, wrong current password, wrong OTP
code ×4, invalid/expired magic link ×2) threw a bare string instead of
`{code, message}`, falling back to `AllExceptionsFilter`'s generic
`HttpStatus[status]` code. No user-facing impact (status/message were
always correct), but made the response's `code` field unable to
distinguish, e.g., a wrong password from a stale session — both
`"UNAUTHORIZED"`. Gave each its own catalog code, exact message text
unchanged.

Added a clean `ThrottlerException` → 429 `TOO_MANY_REQUESTS` mapping —
`@nestjs/throttler`'s default exception previously leaked
`"ThrottlerException: Too Many Requests"` verbatim with no code at all.
Flagged (not fixed) that 429 responses still carry no `Retry-After`
header — doing so would require overriding `ThrottlerGuard` itself, out
of this phase's "mapping layer" scope.

Added a genuine log-capture test
(`packages/observability/src/logger.spec.ts`) that builds a real pino
logger and asserts captured output never contains a raw password/token/
OTP/cookie value. Discovered mid-implementation that pino's default
destination bypasses `process.stdout.write` entirely (writes directly to
the fd via sonic-boom), making a naive `vi.spyOn(process.stdout, "write")`
silently capture nothing — caught by the test's own sanity assertion
before it could have shipped vacuously passing. Fixed by refactoring the
logger into a `createLogger(destination?)` factory so tests can inject a
real in-memory stream.

## Why

The task's own checklist (9 per-error questions × every HTTP status
family × every named code, plus "one mapping layer," "no generic
something went wrong," log scrubbing, and metrics/alerts) is fundamentally
a correctness-and-honesty audit of error handling, not new feature work —
the value is in actually triggering each documented behavior with a real
test, the same discipline this workstream has applied to login/OTP/OAuth/
UI since Phase 2, now applied to the error-response layer specifically.
