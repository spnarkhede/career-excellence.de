# 2026-10-07 — Phase 4 — v0.5.0

## What changed

Replaced the password policy with NIST SP 800-63B (minimum 8, hard cap 128, no
composition rules, every printable character allowed), added a client-safe strength
estimate and policy text to the signup page, and switched password hashing to
explicit OWASP argon2id parameters with rehash-on-login. Added an optional,
feature-flagged breached-password check against the HIBP k-anonymity range API
(fails open on any error).

Rewrote signup to be timing/response-neutral between new and existing emails: the
password is always hashed (and, if enabled, breach-checked) before ever branching on
whether the account exists, a duplicate creates nothing and notifies the real account
owner by email, and the caller always sees the same response shape. Resend now
invalidates older verification tokens before issuing a new one, and a new
`/auth/resend-verification` endpoint is rate-limited per IP and per email. Email
verification now returns one of 5 distinct states (valid/expired/already_used/
invalid/already_verified) instead of a single generic error. Rewrote the verify-email
page with a Confirm button (no auto-POST on load), `referrer: no-referrer`, and the
token stripped from the visible URL on load.

Found and fixed a real, high-severity bug while writing this phase's own tests:
`login()` never checked for an unverified account at all — the email-verification
gate could be silently bypassed from day one.

## Why

This phase's checklist is specifically about signup, password creation, and email
verification being both usable and resistant to enumeration/timing attacks. NIST
800-63B's guidance (no composition rules, generous length limits, optional breach
checking) replaces an older, more restrictive policy that research shows pushes users
toward predictable patterns without improving real security. The timing/response
neutrality for duplicate signups, the Confirm-button verification flow, and the
distinct-but-non-leaking verification states are all specific, testable
anti-enumeration and anti-automation requirements named directly in this phase's
tasks — writing the test for each one (per AUTH_RULES.md rule 8) is what surfaced the
unverified-login bug, which existed since Phase 3 and had no test until now.
