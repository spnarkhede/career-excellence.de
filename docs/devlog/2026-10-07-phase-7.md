# 2026-10-07 — Phase 7 — v0.8.0

## What changed

Switched access-token signing from the shared-secret HS256 used since Phase 3 to
asymmetric RS256, with a `kid` header enabling key rotation, an explicit algorithm
allowlist (rejects `alg: none`), and `iss`/`aud`/`exp`/`nbf` checks with a 5-second
clock-skew tolerance. Added a refresh-token reuse grace window: a rotated token
replayed within 10 seconds resolves to the live session (handling two tabs racing
to refresh, or a client retrying a request it never saw the response to) instead of
revoking the whole family, while a replay outside the window still does exactly
that, unchanged from Phase 3's original reuse-detection design.

Added idle-timeout and absolute-expiry enforcement to `SessionGuard` (which also
now updates a session's last-activity timestamp on every authenticated request),
plus `Cache-Control: no-store` on every authenticated response. Added a CSRF
guard (double-submit cookie + an explicit Origin re-check beyond CORS) to every
cookie-authenticated state-changing route. Hardened cookies: `API_COOKIE_DOMAIN`
now defaults to unset (host-only cookies, narrower than matching subdomains), the
`__Host-` prefix is applied automatically whenever a cookie is Secure with no
Domain attribute, and the refresh cookie moved to `SameSite=Strict` (the session
cookie stays `Lax`, since it may need to survive a top-level navigation from an
email link).

On the client: `packages/api-client` gained single-flight refresh-and-retry-once
on a 401 (one shared in-flight promise, so N parallel 401s cause exactly one
refresh call), automatic CSRF header attachment, and cross-tab logout sync via
BroadcastChannel with a `localStorage`-ping fallback. Added a session-management
page (`/dashboard/sessions`) and a dashboard logout button that broadcasts to
other tabs. Added authenticated `change-password` (revokes every other session)
and `logout-all-devices` (revokes every session including the caller's) endpoints.

Implementing this phase's own checklist surfaced two real bugs: log redaction
(`packages/observability`) used exact-match key matching, which silently let
`accessToken`/`refreshToken`/`csrfToken` bypass redaction despite `token`/
`refresh` already being listed keywords (BUG-010); and `SessionGuard` read the
session cookie name straight from `process.env` instead of the validated config,
which had no visible effect until this phase's `__Host-` prefix logic made the
controller's actual cookie name diverge from the guard's hardcoded fallback —
caught before ever reaching a real deployment (BUG-011).

## Why

This phase's own spec is almost entirely about closing specific, well-known
session/token attack classes: refresh-token replay (the reuse-detection grace
window), algorithm confusion and key compromise (RS256 + explicit allowlist +
kid rotation), cross-site request forgery against an authenticated session (the
CSRF guard), and token leakage via cookies, logs, or storage (the cookie
hardening and the redaction-gap fix). Each of these is independently testable,
and — same as in Phase 5/6 — writing the test for a specific guarantee ("5
parallel requests cause exactly one refresh," "reuse revokes the family") is what
surfaced the two bugs above.

## Open issues

- Same database limitation as every prior phase, plus no browser testing of the
  new sessions page, dashboard logout button, or real (non-mocked)
  BroadcastChannel behavior in an actual browser.
- RS256 was used instead of EdDSA (the task allowed either) solely because
  `@types/jsonwebtoken@9.0.10` doesn't type `"EdDSA"` yet — not a security
  downgrade, flagged in case a future phase wants to revisit (e.g. via `jose`).
- Potential risk, not yet a decided design: idle-timeout is measured against
  protected-resource access, not against `/auth/refresh` calls themselves — see
  FINDINGS.md for the alternative reading and what changing it would require.
- Login/signup/OTP-verify/magic-link-verify are deliberately NOT behind
  `CsrfGuard` (no valid session exists yet when they're called) — a stricter
  "login CSRF" reading was considered and explicitly scoped out.
- No key-rotation drill (issuing under a new `kid` while still accepting the
  previous one) was exercised against a running system this session.
- Carried forward: the remaining open architecture questions from Phase 1, and
  D6 (TOTP MFA, still unresolved/unimplemented).
