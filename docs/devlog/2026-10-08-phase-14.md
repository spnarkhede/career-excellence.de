# 2026-10-08 — Phase 14 — v0.15.0

## What changed

Built the legal, trust and conversion surface for launch: Privacy and
Terms pages, signup terms-acceptance, a rewritten cookie consent banner,
first-party cookieless analytics, a reviewed single-CTA structure,
enhanced 404/500 pages, a contact form with shared client/server
validation, and 3-layer spam protection.

- **Legal pages**: `apps/web/src/app/privacy/page.tsx` and
  `.../terms/page.tsx`, both visibly marked "Draft — requires legal
  review," with bracketed placeholders for controller/processor/
  retention/contact details rather than fabricated real text. No
  Impressum page was created — nothing in this codebase establishes the
  operator's jurisdiction, and the task's own instruction is conditional
  on being in Germany; documented as a deliberate decision in
  `docs/auth/FINDINGS.md`, not an oversight.
- **Terms acceptance**: `signUpSchema` gained a required
  `termsAccepted: z.literal(true, {errorMap...})` field; `AuthService.signUp()`
  writes a `Consent` row (`{userId, type: "terms", version:
CURRENT_TERMS_VERSION}`) — the pre-existing, previously-unused `Consent`
  Prisma model — inside the same transaction as account creation, so the
  existing "no partial account creation" invariant also covers it.
- **Cookie consent**: rewrote `CookieConsentBanner` with per-category
  (Analytics/Marketing) checkboxes, strictly-necessary always shown as
  on/disabled, a byte-identical Reject/Accept button pair (same variant
  and size, verified by an e2e bounding-box-height check), and a new
  `Footer` component with a "Cookie settings" link that dispatches a
  `CustomEvent` the banner listens for to reopen itself.
- **Analytics**: a first-party, cookieless `HttpAnalyticsProvider`
  (`packages/analytics`) posts to this app's own `/analytics/events`,
  gated on consent, never sending credentials. Server-side
  (`apps/api/src/analytics`), a closed event-name allowlist
  (`signup_started`/`signup_completed`/`login`/`verification_completed`)
  plus a separate value-shape filter strips any property value that
  looks like an email, JWT, or UUID before logging — "never send emails,
  tokens or IDs" was read as a content-shape requirement, not just a
  key-naming one.
- **CTA**: reviewed the existing landing/auth page CTA structure against
  the "single clear CTA" requirement and found it already compliant — no
  code change made.
- **404/500**: `not-found.tsx` gained a suggested-links nav;
  `global-error.tsx` gained a "Go home" link next to its existing retry
  button.
- **Contact form + spam protection**: `apps/web/src/app/contact/*` posts
  to a new `apps/api/src/contact/*` endpoint, validated client- and
  server-side against the same `contactFormSchema` (server authoritative
  via `ZodValidationPipe`). Three independent spam checks — a CSS-hidden
  honeypot field, a minimum-fill-time check, and server-verified
  Cloudflare Turnstile (skips with a logged warning when no secret key is
  configured, never silently treated as "passed") — each failing with the
  byte-identical `SPAM_REJECTED` response, so a bot can't learn which
  check it tripped.

## Why

This phase's task list is explicit about building real, server-enforced
controls rather than cosmetic ones ("Reject as easy as Accept," "server
authoritative," "verified on the server") — every implementation choice
above follows that: validation happens server-side regardless of what the
client does, consent genuinely gates the network call rather than just
hiding a banner, and the spam checks are indistinguishable from each
other in their response specifically so a bot can't use the response to
tune its approach.

## Bug found and fixed this phase

**BUG-026** (see `docs/auth/FINDINGS.md`): a granted analytics consent
never actually resulted in a tracked event on a fresh page load. Root
cause had two layers, both the same shape: `CookieConsentBanner` and
`AnalyticsBootstrap` are both mounted as root-layout siblings, and each
only re-established state another component depended on
(`consentGranted`, `activeProvider`) inside its own `useEffect`. React
runs a layout's `{children}` mount effects before sibling effects
declared after them in JSX, so a freshly-navigated page's own
`track("signup_started")` call could run while either piece of state was
still at its default — silently dropping the event either way. Neither
of the two literally-required consent tests ("no analytics before
accept, none after reject") caught this, since both describe the
negative case; an extra test checking the positive case did. Fixed by
moving both pieces of initialization to module-evaluation time, which
structurally cannot race against any component's effects, confirmed via
a direct Playwright network-request listener and the full e2e suite.

## Open issues

- Legal content is a placeholder by design — every processor, retention
  period, and contact address on the Privacy/Terms pages needs a real
  legal review before use; not claimed as final.
- Turnstile verification is "Requires configuration" — real server-side
  verification code exists but has nothing to verify against without a
  `TURNSTILE_SECRET_KEY`; no client-side widget was built either, since
  it has no site key to render against in this environment.
- No real email delivery is wired for the contact form — submissions are
  validated, spam-checked, and logged, not actually emailed anywhere.
- No Impressum page — the operator's jurisdiction is not established in
  this codebase; flagged for a human to confirm.
- firefox/webkit Playwright projects were not run (binaries not
  installed in this environment).
- Carried forward: the remaining open architecture questions from Phase 1,
  and D6 (TOTP MFA, still unresolved/unimplemented).
