# 2026-10-07 — Phase 9 — v0.10.0

## What changed

Implemented OAuth/social login for all five named providers (Google,
Microsoft, GitHub, Facebook, Apple) plus a generic OIDC-discovery-driven
adapter for "any other provider," all behind one shared
`OAuthProviderAdapter` interface in `packages/auth/src/oauth/`. Every
provider uses the authorization code flow with PKCE (S256); the four OIDC
providers (Google, Microsoft, Apple, generic) get full ID token validation
(signature via JWKS, issuer, audience, expiry, nonce) through a shared
`verifyIdToken` helper; GitHub and Facebook (plain OAuth2, no ID token)
instead call a userinfo REST endpoint and apply their own email-trust rule.

Each provider's specific quirk from the task list is handled: Google's
`email_verified` claim is used explicitly; Microsoft is multi-tenant
(issuer validated against the token's own `tid` claim) and identified by
tenant+object id, never email; GitHub fetches the email list and uses only
a primary+verified address; Facebook's email can be missing entirely; Apple
signs its own ES256 client-secret JWT, handles the cross-site
`response_mode=form_post` callback, captures the user's name only on first
authorization (it's never sent again), and treats private-relay emails as
normal verified ones.

`OAuthService` implements every account-linking rule from the task: identity
is matched on `(provider, providerAccountId)`, never email alone; an email
collision with an existing account never auto-links (the user is told to
sign in to the existing account and link from settings instead); unverified
provider emails never link; linking an identity already linked to a
different account shows a clear error; unlinking the last remaining
sign-in method is refused. A provider that returns no usable email
(Facebook missing it, Microsoft never trusted) routes through a new
collect-and-verify-an-email sub-flow (`OauthPendingIdentity` table) instead
of ever creating or linking an account from an unverified address.

On the client: "Continue with X" buttons on login/signup (each a full-page
redirect, never a popup — so there's no popup-blocked/closed state to
handle at all), a per-reason `/oauth/error` retry page, the
`/oauth/verify-email` pending-email sub-flow, and a
`/dashboard/connected-accounts` settings page for linking/unlinking.

Caught and fixed a real bug during implementation, before it was ever
committed: the link-mode session check initially used `jwt.decode()` (no
signature verification) instead of the existing `AuthService.verifyAccessToken`,
which would have let a forged, unsigned cookie link a provider identity to
an arbitrary victim account.

## Why

This phase's task list names five specific providers with five specific
quirks, plus a sixth "any other provider" requirement that only makes sense
if the adapter interface is genuinely provider-agnostic — the generic OIDC
adapter exists specifically to prove that, rather than assert it. The
account-linking rules (never auto-link on email collision, never trust an
unverified email, never unlink the last method) are the same class of
security property every prior phase has centered its own checklist on:
closing a specific, well-understood class of account-takeover or
account-confusion risk, each independently testable.

## Open issues

- No real provider credentials exist for any of the five named providers —
  all Requires configuration; Apple additionally needs a paid Apple
  Developer Program enrollment.
- No browser testing of the full redirect round trip (clicking a button,
  completing a real provider's consent screen, landing back on this app)
  was performed.
- D2 (managed auth provider) remains genuinely unresolved; D5
  (Microsoft/GitHub scope) is pragmatically resolved by this phase's own
  task list, the same way Phase 6 resolved D4.
- No federated/provider-side logout — documented in COMPONENTS.md, not
  implemented.
- No provider access/refresh token storage — nothing in this phase calls a
  provider's API after initial sign-in, so none was added.
- Carried forward: the remaining open architecture questions from Phase 1,
  and D6 (TOTP MFA, still unresolved/unimplemented).
