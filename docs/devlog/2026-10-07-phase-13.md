# 2026-10-07 — Phase 13 — v0.14.0

## What changed

Audited the full 38-item security checklist against Phases 1-12's
existing controls and tests before writing anything new — the task's
own instruction ("locate the control built in earlier phases, write an
attack-style test that proves it holds, and fix any gap") makes this an
audit-first phase, not a build-first one.

The audit found that most of the 38 items already had a dedicated
attack-style test from an earlier phase: forged JWTs and alg:none
(Phase 7/10), IDOR via cross-user session/OAuth-account access (Phase
10), database-level RLS (Phase 3), CSRF double-submit (Phase 7), open
redirects (Phase 8/10), user-enumeration-safety (Phases 4/5/6/8), login
lockout with growing backoff (Phase 5), OAuth state/replay validation
(Phase 9), log redaction (Phase 7), and no-stack-trace-in-production
(Phase 12). Five genuine gaps remained, closed this phase with
`apps/api/test/phase13-security-attacks.spec.ts` (21 tests, all actually
run, no database needed for any of them):

- **Self-role-assignment, swept across every endpoint at once**
  (checklist item 5's explicit wording): only `updateProfileSchema` had
  been individually tested for stripping an attacker-supplied `role`
  field; this sweeps all 12 exported Zod schemas in one test, proving
  Zod's default "strip unknown keys" behavior holds for signup, login,
  password reset/change, OTP, magic link, and cookie preferences too.
- **Algorithm-confusion attack on JWT verification**: signs a forged
  token with HS256 using the server's own RS256 PUBLIC key (known to
  anyone, by definition) as the HMAC secret — the classic variant of
  "alg confusion" distinct from the already-covered alg:none and
  wrong-key cases. `AuthService.verifyAccessToken`'s explicit
  `algorithms: ["RS256"]` allowlist rejects it outright.
- **Regression test for BUG-014** (Phase 9's OAuth link-mode forged-JWT
  bypass, caught and fixed before ever shipping) — FINDINGS.md had
  explicitly flagged "no dedicated automated test... Requires manual
  verification" for over three phases. Closed with a real
  `AuthService`/`OAuthController` pair (no mocks on the auth path),
  fed an alg:none-forged and a wrong-key-signed cookie in `mode=link`.
- **CORS wildcard-plus-credentials check**: a direct, explicit assertion
  that `buildCorsOptions` never returns the literal string `"*"` for
  `origin` alongside `credentials: true` — the specific vulnerability
  class this function's own doc comment already claimed to avoid, now
  machine-verified rather than only claimed.
- **Regression test for BUG-013** (password-reset-confirm previously had
  no rate limit at all) — reads the route's actual decorator metadata
  via reflection to confirm it's still throttled, closing a gap where
  the original fix had no automated check of its own.

No new CRITICAL or HIGH finding was produced. Documented
sessions-not-bound-to-IP/User-Agent as a deliberate, reasoned LOW-severity
design decision (mitigated by HttpOnly/Secure/SameSite/refresh-reuse
detection, not IP binding, which would break legitimate mobile roaming)
rather than leaving it an implicit, undocumented gap.

## Why

A security-checklist phase's value is in actually attacking each
control, not re-reading the code and declaring it fine — but re-deriving
tests for everything already covered by 12 prior phases of dedicated
work would be pure waste. The audit-first approach let this phase spend
its effort on the handful of attack surfaces that genuinely had zero
automated coverage, rather than padding the checklist with duplicate
tests for already-proven behavior.
