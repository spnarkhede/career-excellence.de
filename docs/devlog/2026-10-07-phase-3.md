# 2026-10-07 — Phase 3 — v0.4.0

## What changed

Rebuilt the database schema to match this phase's exact spec: `users` gained
`passwordHash`, `failedLoginCount`/`lockedUntil`, `deletedAt`, and a `citext` email
column for case-insensitive uniqueness; `auth_identities` was replaced by
`users.passwordHash` (direct) + a new OAuth-only `oauth_accounts` table;
`verification_tokens` became `one_time_tokens` with a proper `purpose` enum;
`security_events` became `auth_events` with `ipHash`/`requestId` instead of a raw IP.
`sessions` gained `familyId` (for refresh-token-reuse detection), `absoluteExpiresAt`
(a ceiling that rotation never extends), and `ipHash`.

Enabled Postgres row-level security as defense-in-depth: an `app_anon` role with zero
grants, and an `app_authenticated` role scoped to its own rows via a session variable,
on every auth table. `apps/api`'s actual database connection is unaffected — it
remains the schema owner and continues to bypass RLS exactly as before; the policies
exist to be independently testable and to give a future phase a real second
enforcement layer to build on if Postgres is ever exposed more directly.

Rewrote `AuthService.signUp` to create the user, profile, and default role in one
transaction (closing a gap flagged as a known bug back in Phase 0), moved password
verification from an in-memory stub provider directly onto `users.passwordHash`
(argon2id), and added login lockout and refresh-token-family revocation on reuse
detection. Added `scripts/check-db-consistency.ts` and updated the seed script to
create generated test users.

## Why

This phase's explicit goal — "a newly authenticated user always obtains exactly one
correct profile and the correct permissions, and no user can read or change another
user's data" — required both a schema that actually enforces the stated invariants
(unique case-insensitive email, cascading deletes, RLS) and an application layer that
can no longer leave a user half-created. The password-storage move was mandated by
the schema spec itself (`users.password_hash`) rather than chosen independently, and
incidentally resolved a previously-flagged Confirmed bug (stub provider's in-memory
credential store not surviving a process restart).

## Open issues

- **No live database was available in this session** (no Docker; port 5432 is
  occupied by an unrelated pre-existing Postgres instance on this machine with
  unknown credentials — not probed further). Every migration was generated via
  schema-to-schema diffing (no connection required) and every DB-dependent test was
  written as a real integration test, not a mock, but none were executed against a
  real database. CI will run all of them for real on the next push
  (`migrate:deploy` → `db:seed` → `test` → `db:check-consistency`); if anything fails
  there, it must be investigated and recorded in `docs/auth/FINDINGS.md` before this
  phase can be considered genuinely done, per `AUTH_RULES.md` rule 13.
- A draft of this phase's migration (now fixed) would have corrupted every foreign
  key relationship on a populated database — see `FINDINGS.md` BUG-006. It never ran
  anywhere; flagged for awareness of how close this came to being a serious incident
  had it been generated and applied without review.
- Carried-forward open question: should a future phase wire `app.current_user_id`
  into Prisma's actual connection, making RLS the real enforcement layer?
- Documented decision, not a defect: soft-deleted accounts' emails are never released
  for reuse.
